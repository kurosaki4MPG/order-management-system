# STEP76 非機能要件確認

この手順書は、注文管理システムの非機能要件を確認し、現状の制約と改善候補を整理するための記録である。

このSTEPでは、性能、可用性、保守性、運用性、セキュリティを分けて見直し、どこに負荷や障害が寄りやすいかを把握する。

## 目的

- 画面、API、Lambda、AWS サービスの非機能上の特徴を説明できるようにする
- どこがボトルネックになりやすいかを把握する
- 障害時の復旧しやすさと監視しやすさを確認する
- 保守や運用の観点で改善候補を整理する

## 前提

- STEP74 で全機能統合が確認されている
- STEP75 で注文管理業務フローが確認されている
- 開発環境と AWS の dev 環境にアクセスできる
- CloudWatch、Step Functions、SQS / DLQ、Cognito、S3 を確認できる

## このSTEPで扱う範囲

このSTEPでは、次の 5 つを確認する。

- 性能
- 可用性
- 保守性
- 運用性
- セキュリティ

## 1. 性能を確認する

### 1.1 画面の体感速度

確認対象:

- `/orders`
- `/orders/[id]`
- `/pdf-preview`

確認手順:

1. ブラウザで各画面を開く
2. 初回表示までの待ち時間を確認する
3. 再表示時の速度も確認する
4. 画像、PDF、一覧描画、フォーム入力の重さを確認する
5. DevTools の Network と Performance で遅い箇所を確認する

確認ポイント:

- 一覧表示は業務操作を妨げない速度か
- PDF プレビューは許容できる待ち時間か
- 再訪時に明らかな改善があるか

### 1.2 API の応答時間

確認対象:

- `GET /api/orders`
- `GET /api/orders/[id]`
- `POST /api/orders`
- `GET /api/pdf/invoice`
- `GET /api/pdf/invoice/store`
- `GET /api/pdf/invoice/signed-url`

確認手順:

1. `curl` で各 API を呼び出す
2. `time` を付けておおよその応答を測る
3. 失敗時の応答も確認する
4. 必要なら CloudWatch Logs で遅い処理を追う

確認ポイント:

- 同じ操作で極端に時間差が出ないか
- 生成系 API が画面を待たせすぎていないか
- 同期処理に寄せるべきでない処理がないか

### 1.3 非同期処理の遅延

確認対象:

- EventBridge
- Step Functions
- SQS
- DLQ

確認手順:

1. 注文登録を 1 件実行する
2. `OrderCreated` からワークフロー開始までを見る
3. `prepare`、`finalize`、`invoice` の流れを追う
4. 失敗時は DLQ とアラームがどこで反応するかを見る

確認ポイント:

- 非同期処理が遅れても最終的に追いつくか
- 失敗がどこで止まるか説明できるか
- 再実行の起点が分かるか

## 2. 可用性を確認する

### 2.1 アラームと復旧

確認対象:

- CloudWatch Alarm
- CloudWatch Logs
- Step Functions の Execution
- SQS の DLQ

確認手順:

1. 意図的にエラーを起こす
2. どのアラームが上がるか確認する
3. 原因ログを確認する
4. 修正後にアラームが `OK` に戻るか確認する
5. 同じ入力で再実行できるか確認する

確認ポイント:

- 障害の検知が遅すぎないか
- 原因特定に必要な情報が残るか
- 復旧後に正常系へ戻せるか

### 2.2 DLQ と再処理

確認対象:

- `oms-dev-order-processing-dlq`
- `maxReceiveCount`

確認手順:

1. 不正メッセージを投入する
2. 受信失敗後に DLQ に落ちることを確認する
3. `maxReceiveCount` に達したときの挙動を確認する
4. 手動で削除した後にアラームが戻るか確認する

確認ポイント:

- 失敗メッセージが埋もれないか
- 手動対応の手順が追えるか
- 複数回失敗しても扱い方が一貫しているか

### 2.3 復旧フローをまとめる

障害検知から正常復帰までの流れは、次の順で見る。

1. CloudWatch Alarm または Step Functions の失敗で障害を検知する
2. CloudWatch Logs と DLQ で原因を特定する
3. 原因となっている入力、設定、コードを修正する
4. DLQ を空にし、必要なら再処理または再実行を行う
5. 同じ入力で正常系が通ることを確認する
6. 5分前後待ってアラームが `OK` に戻ることを確認する

この流れを 1 つにまとめておくと、復旧後の確認漏れを減らせる。

## 3. 保守性を確認する

### 3.1 責務分離

確認対象:

- Next.js 画面
- API route / Lambda
- repository / service / schema
- invoice 生成ロジック

確認手順:

1. 画面、API、AWS の責務を書き分ける
2. 共通処理がどこにまとまっているか確認する
3. 環境変数や runtime config の依存を確認する
4. 変更時に触るファイル数を見積もる

確認ポイント:

- 1 つの変更が広い範囲に波及しすぎないか
- 共通化しすぎて読みにくくなっていないか
- 例外処理や権限処理が散らばっていないか
- `requestId` / `eventId` / `orderId` / `workflow` のような追跡キーを揃えることで、実装と手順書の検索軸を一致させる

### 3.2 テストしやすさ

確認対象:

- Vitest のユニットテスト
- API のテスト
- E2E テスト
- 画面の表示テスト

確認手順:

1. `npm run test`
2. `npm run test:coverage`
3. `npm run lint`
4. `npx tsc --noEmit`
5. 失敗時にどの層の責務か判断できるか確認する

確認ポイント:

- テストが実装の都合に引きずられすぎていないか
- 異常系を追加しやすい構造か
- 画面と API の境界が明確か

## 4. 運用性を確認する

### 4.1 ログ追跡

確認対象:

- `requestId`
- `eventId`
- `orderId`
- `workflow`

確認手順:

1. 1 件の注文を登録する
2. CloudWatch Logs で関連ログを追う
3. `aws logs tail` と Logs Insights を使い分ける
4. API と Lambda の両方で同じキーが使われているか確認する

確認ポイント:

- 障害時にログを横断して追えるか
- 検索キーが統一されているか
- 手順を知らない人でも辿れるか

### 4.2 デプロイと再現性

確認対象:

- GitHub Actions
- CDK deploy
- Docker build

確認手順:

1. 変更を push したときの workflow を確認する
2. ローカルで再現できる手順があるか確認する
3. CDK の synth / deploy の前提が整理されているか確認する

確認ポイント:

- 手元と CI で結果が大きくずれないか
- 失敗したときの切り分けが可能か
- 依存キャッシュや前提コマンドが明確か

## 5. セキュリティを確認する

### 5.1 認証・認可

確認対象:

- Cognito
- viewer / operator / admin
- 403 / forbidden

確認手順:

1. それぞれのロールでログインする
2. 画面に出る操作が一致するか確認する
3. 直接 API を叩いても権限制御が効くか確認する
4. 401 / 403 の出し分けを確認する

確認ポイント:

- 画面だけでなく API 側でも守られているか
- 権限違反の導線が分かりやすいか
- 開発時にロール差を追いやすいか

### 5.2 帳票と S3

確認対象:

- PDF 保存
- signed URL
- `PDF_INVOICE_BUCKET_NAME`

確認手順:

1. 請求書 PDF を保存する
2. S3 に正しいオブジェクトが置かれるか確認する
3. signed URL で期限付き参照できるか確認する
4. 不要な公開になっていないか確認する

確認ポイント:

- 参照 URL が恒久公開になっていないか
- 保存先と参照方式が分離されているか
- 環境変数の誤設定を検出しやすいか

## 6. 改善候補を整理する

このSTEPでは、次のような改善候補を記録する。

- PDF プレビューの初回表示を軽くする
- 画面遷移を待たせすぎない構成にする
- エラー文言を利用者向けに分かりやすくする
- ログのキー設計をさらに統一する
- CI の失敗原因を見つけやすくする
- ドキュメントの確認手順を短く、再現しやすくする
- 手順書依存の強い確認は、コマンド例と前提条件を近くに置いて再現しやすくする

次を満たせば STEP76 は完了である。

- 性能、可用性、保守性、運用性、セキュリティを分けて説明できる
- どこが弱点になりやすいかを言語化できる
- 障害時の復旧経路を説明できる
- 改善候補を優先度付きで整理できる
