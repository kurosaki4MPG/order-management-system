# Phase 9 詳細設計書

## 1. 目的

注文管理システムを最終統合し、実務に近い模擬案件として完成させる。

対象STEP:
- STEP74 全機能統合
- STEP75 注文管理業務フロー完成
- STEP76 非機能要件確認
- STEP77 負荷・障害試験
- STEP78 ドキュメント作成
- STEP79 コードレビュー
- STEP80 成果物整理

---

## 2. 統合方針

- フロントは Next.js の画面と API 呼び出しを担う
- API は認証・認可・入力検証・業務ロジックの入口を担う
- DynamoDB は注文データの永続化を担う
- EventBridge / SQS / Step Functions は非同期処理と後続フローを担う
- React PDF / S3 / signed URL は請求書出力を担う
- Cognito / IAM は認証・認可・運用権限を担う
- CloudWatch は監視と障害追跡を担う

これらをひとつの注文管理業務フローとしてつなぐ。

---

## 3. 業務フロー

1. Cognito でログインする
2. 注文一覧を開く
3. 注文を登録・更新・確認する
4. ステータスを変更する
5. EventBridge で後続処理を起動する
6. Step Functions で注文処理ワークフローを進める
7. 請求書を生成して S3 に保存する
8. 署名付き URL で請求書を取得する
9. 通知と監視で実行結果を追う

---

## 4. 非機能観点

- 性能: 画面表示、API 応答、PDF 生成、非同期処理の遅延を確認する
- 可用性: アラーム、DLQ、再実行、復旧手順を確認する
- 保守性: レイヤごとの責務分離とテストのしやすさを確認する
- 運用性: CloudWatch Logs / Insights、AWS CLI、GitHub Actions の確認手順を残す
- セキュリティ: Cognito、IAM 最小権限、同一オリジン確認、署名付き URL を確認する

---

## 5. 負荷・障害試験

- 一定負荷をかけて、一覧、詳細、PDF プレビューの応答性を確認する
- `shouldFailInvoice` や DLQ、Step Functions 失敗を使って意図的に障害を起こす
- 再実行、再デプロイ、アラーム復帰、SQS/DLQ の状態戻りを確認する
