## 4. レビュー観点

### 4.1 命名

- 変数名、関数名、ファイル名が役割を表しているか
- `requestId` / `eventId` / `orderId` などの検索キーが統一されているか
- 環境変数名が用途ごとに明確か

### 4.2 実装の重複と簡潔性

- コードロジックとして重複しているものがないか
- 共通化すべき処理が適切に共通化されているか
- 実装がシンプルでエレガントか
- 同じ意味の処理が複数箇所に分散していないか
- 余計な分岐や二重実装で可読性が落ちていないか

### 4.3 責務分離

- 画面、API、サービス、リポジトリの役割が混ざっていないか
- AWS SDK 呼び出しが必要な層に閉じているか
- UI の表示ロジックとデータ取得が分かれているか

### 4.4 エラー処理

- 予期できる失敗に適切なメッセージがあるか
- API の 400 / 401 / 403 / 404 / 500 の出し分けが明確か
- 障害時に CloudWatch から追いやすいか

### 4.5 テスト

- 正常系と異常系の両方が揃っているか
- モックしすぎて実装の意味が失われていないか
- E2E と単体テストの責務が分かれているか

### 4.6 運用性

- 手順書を見れば復旧できるか
- アラームとログの見方が資料に残っているか
- 本番相当の設定値がどこで管理されるか分かるか

---

## 5. レビューの進め方

### 5.1 まず確認する順番

1. README と Phase 9 の資料を読む
2. 画面から業務フローを追う
3. API とサービスの責務を追う
4. AWS / IaC の設定を確認する
5. テストでカバーできていない箇所を探す

### 5.2 指摘の書き方

- 何が問題か
- どこに出ているか
- どう直すか
- 直さない場合の理由

### 5.3 判断の分け方

- 直すべきもの
- 許容できるもの
- 今後の改善候補

### 5.4 指摘記録テンプレート

レビュー結果は、次の形式で残す。

| 項目 | 記入内容 |
| --- | --- |
| 重要度 | 高 / 中 / 低 |
| 観点 | 命名 / 重複と簡潔性 / 責務分離 / エラー処理 / テスト / 運用性 |
| 対象 | ファイル名、関数名、画面名、API 名など |
| 指摘内容 | 何が問題かを 1 行で書く |
| 根拠 | 再現手順、ログ、差分、設計書との不一致など |
| 影響 | 何が壊れるか、何が読みにくくなるか、どこに不整合が出るか |
| 対応方針 | 修正する / 保留する / 今回は許容する |
| 修正案 | どう直すかを簡潔に書く |
| 補足 | 共通化の要否、代替案、保守上の注意など |

記録例:

- 重要度: 高
- 観点: 重複と簡潔性
- 対象: `src/features/orders/utils/order-id.ts` と `src/lambda/order-create-handler.ts`
- 指摘内容: 注文 ID 生成ロジックが複数箇所に分散している
- 根拠: 同じ命名規則が別実装になっており、将来の変更時に不整合が起きやすい
- 影響: 注文登録と Repository で ID 形式がずれる可能性がある
- 対応方針: 修正する
- 修正案: 共通関数へ集約し、呼び出し側は共通関数を使う
- 補足: 命名とテストも同時に揃える

## 9. レビュー結果

- `src/features/orders/utils/order-id.ts` に注文 ID 生成を共通化し、`src/lambda/order-create-handler.ts` と `src/features/orders/repositories/dynamo-db-order-repository.ts` から同じロジックを使うようにした
- `src/features/pdf/invoice-order.server.ts` の請求書番号抽出を legacy 形式に合わせ、既存注文でも末尾の注文識別子を追えるようにした
- `src/app/api/pdf/invoice/route.ts`、`src/app/api/pdf/invoice/store/route.ts`、`src/app/api/pdf/invoice/signed-url/route.ts` で同じ注文なら同じ請求書情報になるように統一した
- 重複していた ID 生成と時刻依存の揺れは、共通関数化と入力時刻の固定で解消した
- `src/app/login/page.tsx` と `src/components/layouts/app-header.tsx` の認証導線を通常のブラウザ遷移に直し、Cognito への遷移で発生していた CORS エラーを解消した
- `src/features/pdf/invoice-document.tsx` の請求先名は、太字描画時に先頭文字が欠ける現象が実機確認で出たため、`fontWeight: 400` に変更して改善した
- この PDF フォント問題は、実データと生成ロジックに欠落がないことを確認したうえで、`@react-pdf/renderer` の公式 Fonts ドキュメントと、カスタム日本語フォントや `fontWeight` に関する既知事例を照合して、太字描画経路の相性問題として整理した

- legacy データとの互換性も確認済みで、STEP79 のレビューは完了とみなせる
- 認証導線も確認済みで、Cognito ログイン時の CORS エラーは解消した
