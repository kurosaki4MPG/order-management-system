# STEP79 コードレビュー

## 1. 目的

注文管理システムの実装を、設計・責務分離・命名・テスト・運用性の観点で見直す。  
このSTEPでは、修正が必要な箇所と、現状のまま残してよい箇所を分けて記録する。

---

## 2. 前提条件

- STEP74, STEP75, STEP76, STEP77, STEP78 が完了している
- 主要機能の実装とテストが動いている
- Phase 9 の手順書と設計書が更新されている

---

## 3. レビュー対象

### 3.1 画面

- App Router のページ
- PDF プレビュー画面
- 注文一覧、詳細、登録、編集画面
- 認証・認可のガード

### 3.2 API とサービス

- 注文登録、取得、更新、削除 API
- PDF 生成、保存、署名付き URL API
- Cognito 認証セッション処理
- フロントと AWS の接続処理

### 3.3 AWS / IaC

- CDK スタック
- Lambda、DynamoDB、SQS、DLQ、Step Functions
- CloudWatch アラームとログ設定
- GitHub Actions のデプロイ定義

### 3.4 テスト

- Unit テスト
- Integration テスト
- E2E テスト
- カバレッジレポート

---

## 4. レビュー観点

### 4.1 命名

- 変数名、関数名、ファイル名が役割を表しているか
- `requestId` / `eventId` / `orderId` などの検索キーが統一されているか
- 環境変数名が用途ごとに明確か

### 4.2 責務分離

- 画面、API、サービス、リポジトリの役割が混ざっていないか
- AWS SDK 呼び出しが必要な層に閉じているか
- UI の表示ロジックとデータ取得が分かれているか

### 4.3 エラー処理

- 予期できる失敗に適切なメッセージがあるか
- API の 400 / 401 / 403 / 404 / 500 の出し分けが明確か
- 障害時に CloudWatch から追いやすいか

### 4.4 テスト

- 正常系と異常系の両方が揃っているか
- モックしすぎて実装の意味が失われていないか
- E2E と単体テストの責務が分かれているか

### 4.5 運用性

- 手順書を見れば復旧できるか
- アラームとログの見方が資料に残っているか
- 本番相当の設定値がどこで管理されるか分かるか

---

## 5. レビューの進め方

### 5.1 まず確認する順番

1. README と Phase 9 の資料を読む
2. 画面から業務フローを追う
3. API とサービスの責務を追う
4. AWS / IaC の設定を確認する
5. テストでカバーできていない箇所を探す

### 5.2 指摘の書き方

- 何が問題か
- どこに出ているか
- どう直すか
- 直さない場合の理由

### 5.3 判断の分け方

- 直すべきもの
- 許容できるもの
- 今後の改善候補

---

## 6. よく見るポイント

- 本番で困る前に気づくべき設定漏れがないか
- 将来の改修で壊れやすい依存がないか
- ドキュメントとコードの説明が一致しているか
- すでに実施した STEP の方針から外れていないか

---

## 7. 完了条件

- レビュー結果が箇条書きで残っている
- 修正対象と保留対象が分かれている
- 改善の優先順位が見える
- 次の STEP80 で成果物整理に進める

---

## 8. 実施メモ

- 指摘は感想ではなく、再現可能な事実で書く
- 仕様変更を伴う場合は設計書と手順書への影響も一緒に見る
- レビュー後は、必要な修正だけを最小限で行う
