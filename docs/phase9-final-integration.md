# Phase 9 最終統合・模擬案件

対象STEP:
- STEP74 全機能統合
- STEP75 注文管理業務フロー完成
- STEP76 非機能要件確認
- STEP77 負荷・障害試験
- STEP78 ドキュメント作成
- STEP79 コードレビュー
- STEP80 成果物整理

## STEP74 全機能統合

STEP74 の詳細実施手順は [phase9-step74-full-integration.md](./phase9-step74-full-integration.md) を参照する。

実施内容:
- Next.js の画面、API Gateway / Lambda、DynamoDB、EventBridge、SQS / DLQ、Step Functions、Cognito、CloudWatch を一連の流れとして確認する
- 注文登録から一覧、詳細、更新、削除、帳票プレビュー、S3 保存、署名付き URL、通知までを通して確認する
- dev / prod の切り替えが壊れていないかを確認する

確認観点:
- ログイン後に注文操作と帳票操作を途切れずに行える
- API、非同期処理、監視のつながりを説明できる
- 画面遷移、権限、エラー表示、再実行の流れが揃っている

完了条件:
- システム全体が 1 つの業務システムとして動く

## STEP75 注文管理業務フロー完成

実施内容:
- 受注から請求書生成、保存、通知、監視までを通す
- `admin` / `operator` / `viewer` の役割分担を確認する
- フロント、API、AWS の責務が説明できる状態にする

確認観点:
- 注文登録、更新、削除、請求書生成、ダウンロードまでの流れを説明できる
- 権限ごとに見える画面と実行できる操作が一致している

完了条件:
- 注文管理の模擬業務フローが成立する

## STEP76 非機能要件確認

実施内容:
- 性能、可用性、保守性、運用性、セキュリティを確認する
- どこがボトルネックになりやすいかを洗い出す
- 今後の改善候補を明文化する

確認観点:
- 画面、API、Lambda、S3、Step Functions の制約が見える
- 障害時の復旧しやすさや監視の粒度が確認できる

完了条件:
- 非機能観点の弱点と改善案が整理される

## STEP77 負荷・障害試験

実施内容:
- 注文登録や PDF プレビューに負荷をかける
- Step Functions、SQS、DLQ、Lambda の失敗を意図的に起こす
- 復旧後に画面とアラームが戻るかを試す

確認観点:
- どの障害がどのアラームに出るか分かる
- 再実行や再デプロイで戻せるか分かる
- ユーザー視点でどこまで使えるか分かる

完了条件:
- 耐障害性と復旧手順を確認できる

## STEP78 ドキュメント作成

実施内容:
- 画面仕様、API 仕様、AWS 構成、運用手順、障害対応手順をまとめる
- 実行した STEP と確認結果を見返せる形にする

確認観点:
- 第三者がリポジトリだけで全体像を追える
- 何を作り、何を確認したかが分かる

完了条件:
- 引き継ぎ可能な資料が揃う

## STEP79 コードレビュー

実施内容:
- 設計の妥当性、命名、責務分離、テスト、運用のしやすさを見直す
- 本番運用で困りそうな箇所を洗い出す

確認観点:
- レビュー観点が明確である
- 修正すべき箇所と許容できる箇所が分かる

完了条件:
- 改善余地と残す理由が整理される

## STEP80 成果物整理

実施内容:
- 最終版の README、設計書、手順書、実装、テストを整理する
- リポジトリを第三者が追いやすい状態にする
- 次に学ぶべき内容や実案件への持ち込み方を整理する

確認観点:
- 成果物の場所と役割が明確である
- 学習案件として完結している

完了条件:
- 学習案件として完了し、見返しやすい状態になる

## まとめ

- Phase 9 は、これまでに作ったフロント、API、AWS、認証、監視、帳票、テスト、CI/CD をひとつの業務システムとしてまとめる最終段階である
- 実務上は「動くか」だけでなく、「説明できるか」「障害時に戻せるか」「第三者が追えるか」までを完了条件に含める
- 詳細な操作や確認は、各 STEP の個別手順と Phase 8 までの運用知識を前提に進める
